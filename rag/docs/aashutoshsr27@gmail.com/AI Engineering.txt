As
powerful foundation models (LLMs) become accessible building blocks through APIs, the industry’s focus is shifting from creating AI-powered applications from scratch to applying these LLMs to build products rapidly. This shift has given rise to a new demand for specialized expertise, leading to the emergence of AI Engineering, a new discipline bridging the gap between machine learning and traditional software engineering.
If you’re a software engineer, data scientist, or product leader wondering how this shift impacts your work and what skills are now valuable, this article provides a clear breakdown.
A Familiar Pattern of Technological Disruption
History consistently shows that while new technologies often make certain jobs obsolete, they create new roles and opportunities simultaneously. The profession of the “knocker-upper,” tasked with waking people for work, vanished with the alarm clock, but this shift created new work in manufacturing. Similarly, the widespread adoption of computer word processors changed the role of typists and created new disciplines like desktop publishing and IT support for office software. More recently, cloud computing didn’t just automate infrastructure provisioning; it also created an entirely new discipline of DevOps to manage the evolving relationship between development and cloud operations. The current disruption to our industries driven by modern AI follows this same pattern. It is less about jobs disappearing and more about the emergence of new specializations needed to harness this technology.
Building a meaningful AI-powered feature was a long and expensive process, often out of reach for smaller startups. Just to build a feature, a team, typically including PhD-level data scientists and ML engineers, would spend six to eight months in deep research: collecting massive datasets, experimenting with model architectures, and trying to integrate a trained ML model into a product. The barrier to entry was high, and many projects failed before reaching a user.
The arrival of powerful, general-purpose foundation models (like the GPT family, Claude, Gemini, and Llama) has significantly changed how AI-powered products are developed. With foundation models accessible via APIs, the starting point of AI features is no longer a blank canvas but a capable, pre-trained, general-purpose model. The challenge has shifted from building a model from scratch to skillfully applying and prompting an existing one to get good results. Incredible AI capabilities can now be prototyped and deployed with much less data, often in a matter of week-worth of experiments, not years. This wider access to AI creates a new reality that calls for the AI Engineer, a new kind of builder.
The term “AI Engineering” has been around and since 2023 was coined by Shwan Wang then popularized by industry thought leader Chip Haven in her book. She chose it to define a discipline distinct from traditional machine learning, arguing that working with foundation models is fundamentally different. So what exactly is different?
From Deterministic Code to Controlling Chaos
The core difference lies in the nature of the systems they build.
Software engineering is, for the most part, the practice of building deterministic systems. You write code with the expectation that, given the same input, it will always produce the same output. The field is built on principles like pure functions, strict data types, and methodologies like Test-Driven Development (TDD). Every component has a clear contract; an API call with specific parameters should yield always a predictable result. When it doesn’t, it’s considered a bug meant to be identified, isolated, and fixed. A well-tested piece of code is a reliable, predictable machine, trusted to perform its function flawlessly millions of times. It won’t just run on my machine, but for everyone who has a working machine.
AI engineering, however, is part of the software engineering discipline who works with non-deterministic systems. LLMs are probabilistic at their core. Their responses are not derived from explicit, programmed logic but are generated based on patterns learned from trillions of data points generated one token at a time. Even when you set all the parameters — temperature, top-p, and even the random seed — there’s no absolute guarantee you’ll get the exact same response every time. It’s in their nature to be probabilistic, just like any other natural phenomenon. Ask an LLM to “write a short, happy poem about computer bugs,” and you might get two different but equally valid poems. This isn’t a bug; it’s a feature of how these models work, a direct consequence of the model generating text one token at a time, with each new token chosen from a probability distribution.
For a software engineer accustomed to exact logic, this can feel like building on shifting sand. For an AI engineer, controlling this non-determinism is the job. This doesn’t mean eliminating the randomness but rather directing it and putting guardrails around it. Engineering with LLMs requires a fundamental shift in mindset from writing precise code that prevents errors to designing resilient systems that anticipate and handle non-deterministic outputs gracefully. The goal is no longer to guarantee a single correct output but to ensure that the range of possible outputs is consistently high-quality, safe, and aligned with what the user wants. The simple JSON output validations before returning an API response won’t cut it. But if you can’t write a simple is_validate_output(response), how do you ensure your AI system works?
A Way of Controlling Non-Determinism: Evaluation-Driven Development
You adopt a new paradigm: Evaluation-Driven Development (EDD).
In traditional testing, you focus on edge cases in your code’s logic. In EDD, you start with data. Let’s take a simple example: building a sentiment analyzer for movie reviews using an LLM.
    1 Curate a “Golden Dataset”: Instead of collecting thousands of data points for training for evaluation, you need a high-quality, representative set of a few hundred examples. You’d manually gather a mix of reviews: some obviously positive, some negative, and — importantly — some tricky ones filled with sarcasm (“This movie was a cinematic masterpiece of mediocrity”). This becomes your ground truth.
    2 Define Your Metrics: How do you measure success? A combination of automated and human-led approaches is often best.• Automated Metrics: These are fast and scalable. For a classification task, you might use Exact Match (expecting only “Positive” or “Negative”). For generative tasks, one common approach is to use another powerful LLM to act as a “judge.” These LLM-as-a-Judge Metrics assess qualities that are hard to define with exact rules, such as relevance, coherence, and factual consistency (to check for hallucinations). Evaluation frameworks like DeepEval and RAGAS have been built to help standardize these metrics and streamline the evaluation process.• Human-in-the-Loop and SME Review: For nuanced or high-stakes applications, automated metrics are not enough. This is where Subject Matter Experts (SMEs) become critical. A lawyer needs to verify the output of a legal AI; a doctor must validate a medical summary. This “human-in-the-loop” process is the ultimate measure of quality, providing the qualitative judgment that automated systems lack. It’s also crucial because automated AI evaluation can be flaky; relying on another LLM as a “judge” can be unreliable, as it may have its own biases or fail to grasp the subtle context.
    3 Iterate and Refine: The development loop for an AI engineer looks like this:• Write a prompt.• Run it against your golden dataset.• Measure the results using your defined metrics (both automated and human).• Analyze the failures, tweak the prompt, and repeat. (while continuously improving your dataset and evaluation criteria)
This iterative, data-centric process is the core workflow of an AI engineer. Instead of perfecting code, you are perfecting prompts and creating workflows based on performance against real-world examples with the help of SMEs. This seems to be a much simpler way of implementing AI-powered features, one could be tempted to question why we need math degrees and Machine Learning PhDs in this LLM era? Let us analyze this in the next section.
Evolving Tech Team: Roles and Relationships
The rise of AI Engineering doesn’t replace existing roles but redefines the tech team as a more collaborative ecosystem. To understand this, it helps to compare the roles and see how they interact.
    • The AI Engineer: Acts as a rapid builder who uses foundational models or those deployed by ML Engineers. They focus on integrating these general-purpose models into products, with expertise in prompt engineering, evaluation-driven development, and orchestrating workflows. A key part of their role is optimizing for cost and performance.
    • The Data Scientist: Starts with a business problem, asking, “What data do we have, and what can it tell us?” With a background in statistics and experimental design, they explore model architectures and determine if a problem needs a custom solution. Their deliverable is often an insight, a prototype, or a recommendation. The Data Scientist use advanced techniques to develop methods to control non-determinism and support the AI Engineer in determining and developing appropriate evaluation metrics to measure and monitor the quality of a solution.
    • The ML Engineer: Transforms prototypes from scientists and AI Engineers into robust and scalable systems. Specializing in infrastructure, MLOps, and LLMOps, they focus on efficient and effective use of infrastructure, build automated data pipelines for processing and versioning, deploy high-performance APIs, and deliver reusable components, agents, and tools that can be used within complex AI-based systems.
    • The Software Engineer: Creates the user interfaces, manages databases, and writes the backend logic that interacts with AI services. They ensure the final application is secure, reliable, and user-friendly, providing a stable foundation for AI features. Also, they collaborate closely with AI Engineers, Data Scientists, and ML Engineers to build end-to-end systems that seamlessly integrate within a brand new or existing systems and products.
A useful analogy for the roles and relationships of this team is the healthcare system. AI Engineers are like family doctors, the first line of defence who can effectively treat a wide range of common problems. But when a problem is particularly complex, you call a specialist. Data Scientists and ML Engineers are those specialists — the surgeons and cardiologists called in when standard treatments aren’t enough.

Consider a customer service bot. An AI Engineer can quickly build a working prototype using LLMs and agentic AI workflow patterns. But if the bot fails on niche questions, we need the specialists. A Data Scientist might analyze the failures and design a better data processing strategy. An ML Engineer then takes that strategy and builds a new pipeline, perhaps working together with the data scientist to fine-tune a custom model to resolve the problem. Finally, Software Engineers and ML Engineers build wrappers and tools allowing the customer service bot to access the knowledge base and precedent cases while ensuring data privacy constraints are respected.
The AI Engineer built the initial system and identified the limitation; the specialists fixed the underlying problem. The result is a better product built on collaboration. Now that we understand the role better, how do we become an AI engineer?
A Practical Roadmap to AI Engineering
Here is a practical roadmap with some of my favourite resources listed at the end of this article to help you transition into AI Engineering:
    • Start with getting a conceptual grasp of how LLMs work. You don’t need a deep mathematical background, but you should understand that they generate tokens based on learned patterns and that this process is inherently uncertain and are tied to the quality and the type of the data they were trained on.
    • Learn techniques from simple zero-shot prompts to more advanced methods like Chain-of-Thought. Understand how different prompting strategies influence model behaviour.
    • Learn the established AI system architectures like RAG, AI Agents, and Tool Calling. These are the common patterns for building AI applications.
    • Get hands-on with creating golden datasets and using evaluation frameworks to practice Evaluation-Driven Development. This is a crucial skill for building reliable systems.
    • Think in Trade-offs. Learn to balance performance, latency, and cost. This includes knowing which model is right for a given task and optimizing token usage to reduce costs.
    • Build Robust Guardrails as a part of the pipeline. A common pitfall is assuming a model will always behave as expected. Learn to build robust input and output validation to catch hallucinations, filter inappropriate content, block malicious use, and ensure your system fails gracefully.
The Path Forward
We are at an interesting disruption point in software engineering. The industry is undergoing a significant transformation, comparable to the advent of the web. The shift from writing precise, deterministic logic to orchestrating and steering powerful, probabilistic systems is changing what it means to be a builder for some of us. And AI Engineering represents this new direction.
This new discipline certainly requires curiosity, a willingness to work with uncertainty, and a focus on evaluation and user experience. It’s less about knowing a single right answer and more about knowing how to ask the right questions of your models, your data, and your users.
For the software engineers of today, this isn’t a threat but rather an invitation. The tools are available, the patterns are emerging, and the opportunity to build the next generation of intelligent and helpful applications is immense.
